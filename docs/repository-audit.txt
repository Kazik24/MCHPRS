History and why integration became difficult
Shared ancestor of original piston fork and fork master: 1f33340 (2024-04-05).
Fork master has 70 subsequent commits; p0.1.0 has 116 divergent commits.
The 1.20.4 piston branches incorporate networking changes but keep redstone,
redpiler, and the World trait/storage inside core. Upstream moved those APIs
into independent crates in 21c694f and 75f3718. The large merge branch mixes
these architectures, including upstream tests expecting crates it removed.
Reflog also records attempted world extraction and resets during October 2024.
The piston engine, redstone update tests, scheduler, and core tests remain
identical between p0.1.0 and the later piston lineage, apart from a comparator
empty-container fix. The protocol and block tables were where most port work
occurred.

Features to preserve from the original fork
Pistons and moving piston entities; piston block actions/animation; observers;
zero-delay scheduling; game/nano/pico tick advancement; piston update ordering,
BUD/instant-circuit behavior and recovery logic; WorldEdit piston rotate/flip;
debug stick and redstone power display; cursed/instant repeater behavior;
block entity memory improvements; schematic error handling and completion.
Pistons and observers are handled by the interpreted engine; Redpiler's
identify_block does not create graph nodes for them. A Piston enum value in
redpiler_graph remains marked TODO. Automatic Redpiler behavior therefore needs
attention during later validation, separately from protocol compatibility.

Proposed port sequence
1. Use version-pinned block/item/entity/sound IDs, preserving fork-specific
   block properties and migrating save data explicitly.
2. Implement login/configuration/play transitions, configuration registry data,
   known-pack exchange, and version-specific packet IDs and fields.
3. Implement anonymous NBT/text encoding and structured item components;
   update creative inventory, equipment, metadata, chat, commands, signs,
   scoreboard packets, chunk data, and block-action encodings.
4. Verify client join, chunk rendering, placement/breaking, reconnect, save/load,
   WorldEdit, and piston animation with a real 1.21.1 client. Keep existing
   simulation behavior and its known failing test visible during the port.
5. After the port, establish reference fixtures and address piston implementation
   discrepancies toward full reference compliance.
The 1.21.1 protocol implementation has not started in this assessment.
